# Python 滨海驾驶游戏分阶段执行计划

项目暂定名：Coastal Drive／滨海驾驶

## 一、目标、范围与执行规则

### 1. 已确认的成品方向

制作一款可以在本机 PyCharm 中开发、运行和调试的 Python 3D 驾驶游戏。

| 项目 | 已确定要求 |
|---|---|
| 首发规模 | 一辆可驾驶汽车、一张完整地图 |
| 地图主题 | 滨海山路，包含海岸、山坡、树林和观景点 |
| 视觉方向 | 风格化写实，车辆比例可信、材质与光照协调 |
| 驾驶手感 | 易上手的拟真街机，键盘可玩，有制动距离、抓地限制与轻微侧滑 |
| 游戏模式 | 公路计时赛、自由驾驶 |
| 交通车辆 | 自由驾驶中提供少量规则控制的车辆 |
| 开发方式 | Python 3.12、PyCharm、独立虚拟环境 |
| 首发平台 | Windows x64 |
| 性能目标 | 本机独显运行，1080p 中档画质以稳定 60 FPS 为目标 |
| AI 范围 | 只建立必要接口与驾驶记录能力，不训练模型、不制作训练界面 |

第一版必须形成完整的游戏流程：启动、主菜单、选择模式、驾驶、暂停、结算或退出、再次开始。

第一版不包含联网、开放世界、车辆改装系统、完整驾驶舱、动态天气、昼夜循环、车辆损坏变形、比赛对手车群、真实城市交通规则或神经网络训练。

计时赛中的幽灵车是历史轨迹回放，不标记为 AI。自由驾驶交通车是规则控制车辆，不宣称为学习型 AI。

## 三、第 1 阶段：建立游戏骨架和仿真接口

**负责人：【高能力模型必做 H0】确认设计；【Luna】实现。**

### 1.1 固定模块职责

项目按下列职责组织，不建立通用引擎框架：

- 程序入口与主循环；
- 仿真世界和车辆；
- 道路与地图数据；
- 玩家输入和控制来源；
- 比赛规则与计时；
- 交通车辆；
- 相机、声音和画面；
- 游戏界面与存档。

开始时允许每项职责用一个小模块实现，只有复杂度确实增加时才继续拆分。不得提前引入插件系统、依赖注入容器或大型 ECS。

### 1.2 确定最小接口

核心接口按以下行为实现，具体内部辅助函数由正常实现需要决定：

| 接口 | 行为 |
|---|---|
| `Control` | 包含转向 `[-1,1]`、油门 `[0,1]`、刹车 `[0,1]` |
| `Simulation.reset(seed)` | 重建场景和车辆初始状态，清除上一局事件 |
| `Simulation.step(control, dt)` | 推进一步仿真，不读取键盘，不更新界面 |
| `Simulation.snapshot()` | 返回供画面、记录和测试使用的只读状态 |
| `Controller.sample(state, dt)` | 返回统一驾驶指令 |
| `Simulation.close()` | 释放物理与相关资源 |

玩家输入、测试驾驶脚本和未来 AI 都走同一控制接口。

`snapshot()` 是仿真状态读取接口，不提前把完整世界状态定义成未来 AI 必须使用的观测。视觉观测和训练观测以后再包装。

### 1.3 时间推进和状态管理

- 物理使用固定 120 Hz 步长，渲染读取插值状态。
- 单个画面帧最多补进 8 个物理步，防止失速后无限追帧。
- 多余积压采取明确的截断策略，并记录诊断事件；不得突然增大物理步长。
- 比赛用仿真时间计时；暂停期间计时停止。
- Headless 测试逐步推进，不应用实时画面帧的积压截断。
- 状态至少包括主菜单、加载、倒计时、驾驶、暂停和结算。
- 窗口失焦自动暂停并清空按键状态，恢复焦点后由玩家主动继续。

游戏主体只能有一套权威车辆状态。不得让界面、相机或交通模块直接改写玩家位置来“修复”问题。

### 1.4 基础验收

- 30、60、144 FPS 的渲染节奏下，固定输入得到近似一致的车辆状态。
- 同一版本、同一机器、相同种子和输入，能在约定误差内复现。
- 暂停 10 秒后，车辆与比赛计时保持不变。
- 连续重开 20 次不遗留车辆、任务或输入监听。
- 无窗口模式能完成 10,000 次物理步进。
- H0 复核确认不存在对 MFC、窗口尺寸或界面控件的仿真依赖。

## 四、第 2 阶段：车辆物理、输入和相机

**负责人：【Luna】搭建；【高能力模型必做 H1】负责物理调校和关键验收。**

这一阶段必须先把车开舒服，再进入正式地图美术。

### 2.1 基础车辆

采用 Bullet 射线车辆：

- 单一车身刚体、四个车轮和悬挂。
- 前轮转向，后轮驱动。
- 车身碰撞体采用盒体或简单组合体。
- 主车质量以 1,250 kg、轴距约 2.6 米为初始调校值。
- 轮径根据实际模型匹配，重心低于可视车身中心。
- 最高车速初始目标约 160 km/h。
- 0～100 km/h 加速目标区间约 8～11 秒。
- 100～0 km/h 平整干燥路面制动目标约 35～50 米。

上述数值是游戏调校目标，不宣称对应某款真实汽车或工程级车辆模型。使用 Bullet 官方车辆能力作为基础。[车辆物理参考](https://docs.panda3d.org/1.10/python/programming/physics/bullet/vehicles)

### 2.2 控制要求

默认键位：

| 操作 | 键位 |
|---|---|
| 油门 | W／上方向键 |
| 刹车、停车后倒车 | S／下方向键 |
| 左右转向 | A/D 或左右方向键 |
| 安全复位 | R |
| 暂停 | Esc |
| 切换追尾距离 | C |
| 显示诊断信息 | F3，仅开发版 |

行为固定如下：

- 转向输入有渐进和回正，不能按键瞬间打满方向。
- 高速最大转向角减小，低速保留足够转弯能力。
- 同时踩油门和刹车时，刹车优先。
- 前进中按 S 先制动；停止并短暂保持后才进入倒车。
- 同时按左右方向时目标转向为零。
- 暂停、失焦、重开、退出驾驶时清空输入。
- R、C、Esc 仅响应按下边沿，不能长按连续触发。
- 第一版不设置专门漂移键，不做手动换挡。

### 2.3 驾驶反馈

- 自动挡提供合理的转速和换挡反馈。
- 松油门有滚阻与空气阻力，不能永远匀速滑行。
- 草地、砂石路肩的阻力和抓地与沥青不同。
- 允许轻微侧滑，不能在普通转弯时无规律翻滚或打转。
- 稳定辅助如有必要，应明确放入车辆控制实现，不能直接强行改车身朝向。
- 所有调校参数集中在车辆配置中。

### 2.4 相机

- 第一版只做两档距离的第三人称追尾相机。
- 相机有平滑跟随和适度前方预瞄。
- 倒车时保持可理解的观察方向，不突然翻转。
- 使用碰撞查询处理地形和墙体遮挡。
- 相机碰撞体不参与车辆实体碰撞。
- 轻微速度视角变化可用，剧烈抖动和运动模糊不作为默认效果。

### 2.5 测试场和验收

测试场包含直道、定圆、S 弯、缓坡、路肩和刚性障碍。

必须完成：

- 加速、制动、倒车与连续转向检查。
- 定圆和 S 弯的稳定性检查。
- 油门、刹车和转向同时输入检查。
- 接触路肩、轻碰护栏、正面撞击和翻车复位。
- 按住油门切出窗口后恢复，不发生卡油门。
- 连续人工驾驶至少 10 分钟。

H1 交付车辆参数、测试指标和实际驾驶证据。若尚未完成人工试玩，只能标记数值与自动化验收通过，不能认定“手感已确认”。

## 五、第 3 阶段：滨海山路与道路碰撞

**负责人：【高能力模型必做 H2】负责几何方案和复核；【Luna】完成实现与场景搭建。**

### 3.1 地图设计

固定制作一张约 2.4～3.0 公里的闭合公路环线：

- 双向两车道，靠右行驶。
- 主路总宽约 8 米，两侧适量路肩。
- 包含滨海直路、山坡连续弯、一个低速发卡弯、林间路段和观景点。
- 最大常规坡度控制在约 6%。
- 第一版不做路口、隧道、立交或道路自交。
- 比赛按一个固定方向运行；自由驾驶可以自行掉头。
- 显著落差或靠海区域布置护栏，海面用于景观展示。

### 3.2 道路数据与生成

使用一份道路中心线与宽度、高度数据，统一生成：

- 可视路面；
- 道路碰撞网格；
- 左右车道路径；
- 护栏与路边设施位置；
- 比赛检查点；
- 小地图；
- 安全复位参考位置。

具体要求：

- 中心线采用平滑曲线并按弧长采样。
- 按曲率调整采样密度，避免发卡弯路面折角。
- 稳定计算道路方向、横向和法线。
- 闭环起终点的朝向、法线、纹理和碰撞连续。
- 纹理按实际道路长度平铺，不能在弯道严重拉伸。
- 路面网格和物理表面使用同一坐标与高度。
- 先生成道路，再使地形与路肩贴合。
- 警示牌和制动提示位于弯前，不能遮挡视线或侵入车道。

### 3.3 碰撞要求

- 地面、道路、护栏、车辆的碰撞类别明确。
- 路标和装饰是否碰撞按用途固定，不让细小装饰随意弹飞车辆。
- 检查点、相机查询和幽灵车使用独立过滤规则。
- 护栏接缝不得产生明显卡车或弹射。
- 高速碰撞考虑固定步长与连续碰撞设置，避免穿越薄障碍。
- 复位位置必须具有有效路面支撑和足够空间。

### 3.4 验收

- 沿整条中心线和两条车道路径进行自动采样，检查路面支撑与高度连续。
- 普通速度跑完全图至少三圈。
- 高速通过闭环接缝、上坡顶端、下坡底端和急弯。
- 在护栏接缝及路肩位置反复接触，不能陷入或被异常弹起。
- 车辆任意落到地图外或翻覆后，都能回到最近已通过的安全位置。
- H2 审查道路可视网格与碰撞网格叠加图。

地图灰盒未通过验收前，不进行大量景物布置。

## 六、第 4 阶段：计时赛、成绩和幽灵车

**负责人：【Luna】实现；【高能力模型必做 H3】复核规则。**

### 4.1 比赛流程

首发计时赛固定为三圈：

1. 从主菜单选择计时赛。
2. 加载地图，在起跑区重置车辆。
3. 三秒倒计时，倒计时期间禁止提前移动。
4. 计时开始，显示当前圈、当前圈用时、上圈和最佳圈速。
5. 第三圈结束后进入结算。
6. 可以重新比赛或返回主菜单。

计时赛关闭交通车辆。

### 4.2 圈数和检查点

- 沿道路顺序设置 16 个检查点，包括起终点。
- 检查点用前后两次车辆位置的穿越关系判断，不能只靠当前帧是否落入触发盒。
- 只有从正确方向、按顺序通过全部检查点后越过终点，才完成一圈。
- 倒着越过终点、在起终点来回移动、漏检查点都不能增加圈数。
- 未通过当前检查点时，不接受后面的检查点。
- 明显离开道路走捷径或使用复位，本圈标记无效。
- 无效圈仍可完成流程，但不更新个人最佳和最佳幽灵车。
- 正常碰撞不自动判无效；其减速和时间损失作为自然代价。
- 暂停不计时。

复位返回最近通过的安全检查点区域，速度清零，不给予新的检查点进度。

### 4.3 成绩与幽灵车

- 保存每圈是否有效、用时和最佳有效圈。
- 幽灵车记录有效最佳圈的仿真时间、位置、朝向与必要的可视状态。
- 按固定频率采样，播放时插值，不再次运行车辆物理。
- 幽灵车不参与碰撞、交通感知和检查点判定。
- 半透明显示，在靠近玩家时减弱显示以免遮挡。
- 记录地图版本和物理配置版本；不兼容的幽灵记录不得强行播放。
- 只在更好的有效圈完成后替换最佳记录。

### 4.4 验收

必须覆盖：

- 正常完成三圈。
- 反向穿越终点。
- 漏掉检查点。
- 高速一步跨过检查点。
- 起终点反复来回移动。
- 捷径、复位、暂停与重新开始。
- 无效圈不会覆盖有效最佳圈。
- 幽灵车在弯道、起终点和暂停恢复后保持连续。
- 删除或破坏幽灵文件后，正常比赛仍可运行并给出清楚提示。

## 七、第 5 阶段：自由驾驶和交通车辆

**负责人：【Luna】实现基础逻辑；【高能力模型必做 H4】负责行为和碰撞整合。**

### 5.1 自由驾驶

- 与计时赛共用同一地图、玩家车辆和物理配置。
- 显示速度、小地图、驾驶距离和运行时间。
- 不计算比赛成绩，不显示比赛检查点。
- 支持暂停、复位和返回菜单。
- 默认生成 8 辆交通车，两个方向各 4 辆。
- NPC 外观可以使用不同颜色和两三种已有车身，不增加玩家选车功能。

### 5.2 交通行为

交通车辆使用相同的基础车辆物理和统一控制指令，不通过直接修改位置沿轨道滑行。

第一版行为限制为：

- 沿自己的车道行驶；
- 根据前方弯道降低目标速度；
- 跟随前车、减速和停车；
- 对停在本车道的玩家作出制动反应；
- 路线闭环循环。

第一版不做超车、随机变道、主动别车或复杂路口让行。

实施默认：

- 巡航速度在约 35～65 km/h 范围内按车辆配置变化。
- 采用路径跟踪控制，结合前方曲率限制速度。
- 跟车依据车道前方车辆和实际净距，不仅依据直线距离。
- 遇到较近静止障碍时执行紧急制动。
- 初始生成位置沿道路分散，具有足够间距。
- 正常运行不在玩家视野内突然生成或销毁车辆。
- 复位前检查交通占用；必要时选择相邻的安全复位点。
- 被碰撞偏离路线后，应停车或尝试恢复；无法恢复的车辆仅在远离玩家视野时重置。

规则交通只能作为可玩的交通背景，不宣传为具备真实道路安全保证的自动驾驶系统。

### 5.3 验收

- 自由驾驶连续运行 15 分钟，交通车能够持续绕图。
- 玩家停在车道上时，后车能在正常初始条件下刹停。
- 车流进入急弯时不会普遍冲出道路。
- 车辆接触后没有持续互相穿透。
- 玩家复位不会落在其他车辆内部。
- 不会因为交通车卡住而阻塞主线程。
- H4 明确区分算法缺陷、碰撞参数问题和地图问题，不用瞬移掩盖错误。

## 九、第 7 阶段：稳定性、性能和 AI 扩展基础

**负责人：【Luna】执行检查；架构缺陷和疑难性能问题【遇阻升级】。**

### 7.1 建立统一性能场景

测试条件固定记录：

- 本机接电；
- NVIDIA 独显；
- 1920×1080；
- 中档画质；
- 正常玩家视角；
- 自由驾驶 8 辆交通车；
- 预热 30 秒后采样 5 分钟。

性能验收目标：

- 关闭帧率上限测量时，平均帧率不低于 60 FPS。
- 帧时间第 95 百分位不高于 25 ms。
- 不出现规律性的长时间停顿。
- 暂停、重开和切换模式后没有持续内存增长。
- 30 分钟运行后，内存应趋于稳定。

达不到目标时，先记录瓶颈再优化，优先检查绘制调用、阴影、模型实例、资源重复加载和 Python 每帧分配。不得直接将默认分辨率降到很低并标记目标已达成。

### 7.2 稳定性检查

覆盖：

- 连续驾驶 30 分钟。
- 连续重新开始 20 次。
- 计时赛与自由驾驶多次切换。
- 窗口切出、恢复、最小化。
- 长按和同时按多个控制键。
- 声音关闭或没有音频设备。
- 存档首次创建、损坏和无法写入。
- 删除可选幽灵记录。
- 资源缺失时给出可定位的错误信息。
- 完整退出后没有残留进程。

关键必需资源缺失时明确报错，不偷偷用方块替代并继续宣称游戏正常。

### 7.3 AI 扩展基础

只实现以下基础能力：

1. 统一驾驶指令已由所有控制来源共用。
2. `reset(seed)` 可重复建立场景。
3. 无窗口模式可运行同样的道路碰撞和车辆物理。
4. 能读取速度、位置、朝向、道路进度、车道偏差及碰撞事件。
5. 能按固定控制频率运行测试控制器，例如 20 Hz 控制、120 Hz 物理。
6. 可记录玩家实际发出的控制指令和对应状态。
7. 记录地图、车辆配置、随机种子和版本信息。
8. 能通过测试用控制器验证输入来源切换，并清理上一来源残留输入。

驾驶数据记录默认关闭，通过开发配置开启，不能每个物理步强制同步写磁盘。

不在此阶段实现奖励函数、Gymnasium 完整包装、训练算法或模型选择界面。后续需要时按 Gymnasium 的标准环境形式适配。[接口参考](https://gymnasium.farama.org/introduction/create_custom_env/)

### 7.4 必须保留的测试

自动化测试集中于确实可能损害体验或数据的行为：

- 输入优先级与清空；
- 固定步长推进；
- 道路闭环与采样；
- 检查点顺序和圈数；
- 有效圈与最佳成绩；
- 幽灵记录兼容性；
- 复位位置；
- 存档读写；
- Headless 仿真。

不为简单赋值、常量和纯界面排列编写大量机械测试。

- 两个游戏模式完整进入和退出。
- 图形、中文、声音和存档全部正常。
- 关闭后重新运行，设置和最佳成绩仍然存在。
- 如无法在没有 Python 的独立环境验证，明确记录该验证缺口，不宣称已经完成独立机器验证。

### 8.4 H6 最终复核清单

高能力模型必须检查：

- 成品是否实现一车一图与两种玩法。
- 车辆是否仍由同一物理核心控制。
- 计时与检查点是否存在明显可绕过问题。
- 交通、复位、幽灵车之间是否相互干扰。
- 性能结论是否来自规定场景。
- AI 接口是否真正脱离键盘与 UI。
- 代码是否存在大量吞异常、重复分支或无必要抽象。
- 画面是否还有明显占位资产、穿插和比例问题。
- 测试是否真实执行，哪些属于待人工验收。
- 旧项目是否保持原样。

### 8.5 最终交付报告

只报告真实结果，至少写明：

1. 游戏源码和可运行程序的位置。
2. 已完成的玩法。
3. 启动方式与键位。
4. 实际性能数据。
5. 自动化、实机和人工试玩分别完成了什么。
6. 已知问题及对使用的影响。
7. 下一阶段接入 AI 时可直接使用的接口。

不能以“后续可以完善”代替首版已要求的菜单、计时、复位、声音、存档、打包或画面验收。

## 十一、代码风格与实施纪律

### 1. 代码风格

- 使用简单直观的类名和函数名。
- 模块围绕车辆、道路、比赛等实际对象划分。
- 仅在存在清楚状态和生命周期时使用类。
- 类型标注优先用于模块接口、控制指令和重要状态。
- 注释解释单位、物理假设、调校原因和复杂判断。
- 不逐行翻译代码含义，不添加大段模板化文档字符串。
- 参数集中管理，但不把所有常量都搬进复杂配置框架。
- 不使用覆盖整个主循环的 `try/except Exception` 吞掉错误。
- 文件读取、资源加载、存档等边界处理真实故障。
- 不为了显得像人工编写而保留坏代码或故意制造不一致。

### 2. 修改范围

- 只处理当前阶段和明确依赖。
- 修复问题时先找原因，不用额外状态标记不断补丁式绕过。
- 发现需要改变公共接口时，先由高能力模型复核并更新计划。
- 美术参数和驾驶参数允许在对应阶段迭代，但必须记录最终采用值。
- 不擅自换引擎、不引入第二套车辆物理、不扩大到开放世界。
- 不把 MetaDrive 或其他大型项目整体拷入作为隐藏依赖。

### 3. 遇阻处理

Luna 遇到问题应先做到：

1. 固定复现条件。
2. 收集最小日志、截图或指标。
3. 区分代码、参数、资源和环境问题。
4. 做一次针对性修复并验证。
5. 第二次修复仍失败时，整理材料升级，不继续盲目尝试。

可以独立继续的工作继续完成；依赖失败项的阶段不虚报完成。

### 4. 阶段通过顺序

执行顺序固定为：

**0 环境与资源 → H0/1 游戏骨架 → H1/2 驾驶 → H2/3 地图 → H3/4 计时赛 → H4/5 交通 → H5/6 画面声音 → 7 稳定性与接口 → H6/8 发布。**

每次进入新阶段，Luna 先读取前一阶段验收结果。最终是否“好玩”必须经过真实驾驶反馈确认，自动化检查负责保证规则、稳定性和可复现性，不能替代人的驾驶体验判断。
