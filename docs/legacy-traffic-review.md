# 旧交通逻辑只读审查

审查范围：`ADAS/CSimulationEngine.cpp`、`ADAS/CSimulationEngine.h`，并对照
`CoastalDrive/src/traffic.py`、`CoastalDrive/src/simulation.py`。旧 C++ 按本机默认编码读取；本文只引用代码结构和行号，未启动旧 EXE/GUI，也未把风险表述为已实测故障。

## 可以继承的意图

1. **行为分层。** `VehicleState::BehaviorState` 把跟车、准备切入、切入、制动、稳定、回原车道、普通变道拆开（`CSimulationEngine.h:23-25`）；更新采用 `nextState/nextTargetLaneIndex` 再统一提交（`CSimulationEngine.cpp:107-111,222-226`）。这个“先决策、后提交”的骨架适合保留。
2. **事件时钟而非每帧随机。** 初始切入延迟 5–15 s（`26-30`），普通车辆变道检查间隔 8–20 s（`127-140`），切入完成后冷却 10–25 s（`179-187`）。新逻辑可继承“每车独立决策时钟、成功后冷却”的意图，但时钟应由可复现 RNG 驱动。
3. **一维相对运动的清晰定义。** 交通车相对玩家按
   `position_y -= (our_speed - vehicle_speed)*dt` 更新（`262-264`），前车目标和 TTC 也使用相对速度（`312-341`）。这种量纲简单、便于日志和回放；现实化时需把它改为道路弧长/车体几何，而不是照搬像素模型。
4. **变道前后都做安全检查。** 普通变道调用 `IsLaneChangeSafe`（`127-140`），切入在接近玩家纵向位置时再次检查目标车道（`144-149`）；安全函数同时考虑最小距离 15 m 和 4 s TTC（`499-568`）。可继承“候选车道先审查、进入关键阶段再复核”的意图。
5. **显式处理冲突、碰撞和离场。** 同一目标车道的同时变道会择一保留（`203-220`），矩形相交会停止仿真并记录主目标（`266-290`），落后于 −150 m 的车会被回收（`343-356`）。这些都是新交通层需要的状态出口。

## 代码风险（静态证据，未实测）

1. **随机性不可复现。** 构造函数用 `random_device` 播种（`CSimulationEngine.cpp:5-9`），方向还使用 `m_rng()%2`（`127-130`）。同样输入无法稳定重放；取模也带轻微分布偏差。新逻辑应注入 seed，并记录每次随机决策。
2. **车辆状态初始化不完整。** `VehicleState` 只有 `toBeRemoved` 有默认值，其他字段无默认初始化（`CSimulationEngine.h:8-25`）。`Reset()` 创建的前车没有设置 `stateChangeTimestamp/cooldownEndTime_s/nextLaneChangeCheckTime_s/nextTargetLaneIndex`（`36-45`）；切入车也未设置若干字段（`47-58`）；`SpawnVehicle()` 同样只填部分字段（`467-486`）。当前路径未必立即读取所有未初始化值，但这是未定义状态进入决策的风险，不能直接复制。
3. **速度扰动不是交通反应。** ID 1 的速度是固定正弦波 `base + 10/3.6*sin(t*0.5)`（`117-122`），并不响应前车间距；普通车生成速度只在 80–110 km/h 均匀抽样（`478-479`）。可继承“速度有差异”的意图，不能把正弦或一次抽样当作现实跟驰模型。
4. **随机变道可能长期无效。** 车辆到检查时随机选左右一侧；越界或不安全后仍立即把下一检查时间推迟 8–20 s（`127-141`）。没有“意图保持/等待合适间隙/换另一侧”的记忆，可能造成与交通状态脱节的稀疏变道。
5. **自动变道接口绕过安全判断。** `ExecuteAutomatedLaneChange()` 只检查车道索引，直接修改车道和横向目标（`424-429`），没有调用 `IsLaneChangeSafe()`；若上层误把它当作执行接口，安全约束会被跳过。
6. **安全判断是中心线近似。** `IsLaneChangeSafe()` 仅以目标车道中心距小于半车道宽筛车（`537-545`），再比较中心点纵向距离/TTC（`549-563`）；没有车体长度、变道持续时间或横向重叠过程。它能表达“目标车道前后都有窗口”的意图，但不足以代表整个变道轨迹。
7. **切入状态有固定脚本色彩。** ID 2 只有在全局触发时间后才准备切入（`123-126`），到 `position_y > -5` 才进入切入（`144-149`），切入完成即固定制动至“初始前车速度−10 km/h”（`152-168`）。这适合演示单一事件，不适合多车、不同速度和道路曲率的普通交通。
8. **并发变道冲突解决依赖位置顺序。** 冲突检测只比较 `nextTargetLaneIndex`，随后按 `position_y` 的大小规律撤销一方（`203-218`），没有优先级、车道方向或变道阶段；双重遍历还可能在后续比较中再次改变结果。可保留“同一目标车道仲裁”，应改成一次性确定胜者。
9. **生成失败不重试。** 新车固定生成在 `position_y=300`，发现同车道横向近且纵向差小于 100 m 就直接 `return`（`465-494`）；调用方随后仍会安排下一次普通生成（`71-76`）。这是“尝试生成”的语义，不是保证交通密度的语义，不能据此假设每个周期都生成成功。
10. **前向车辆可能无界累积。** 旧代码只回收 `position_y < -150` 的车（`343-356`），没有对玩家前方过远车辆的生命周期处理；若车辆速度不低于玩家，它们可能长期留在容器中。此处是潜在容量/密度风险，未通过运行观察确认。
11. **后车 TTC 警告只覆盖当前车道。** `GetLaneNeighbors(m_nOurCarLane)` 只找当前车道最近前后车（`292-310,433-462`），且报警只看后车追近。它不能直接回答“目标车道后车是否会在变道期间逼近”，新逻辑应分别计算当前车道和候选车道。

## 与当前 Python 实现的边界

- `traffic.py:83-120` 已有前视曲率限速、车体外接尺寸、前车净间距、舒适停车间隙和制动触发；这是比旧 C++ 正弦速度更适合继承的基础。旧 C++ 的 15 m/4 s 阈值只能作为待标定参数，不能直接替换 Python 的几何间隙。
- `traffic.py:49-72` 的 `Driver.recovering` 是受姿态/偏离车道触发的制动恢复状态；可借鉴旧状态机“显式恢复态”的写法，但不要把旧的固定切入/回原车道脚本并入恢复逻辑。
- `simulation.py:176-209` 用 seed 建立交通初态；`211-229` 每车计算控制；`334-362` 固定 1/120 s 步进，并每 6 tick 驱动交通。这些边界比旧 C++ 的任意 `timeStep` 更适合做确定性回放。
- `simulation.py:231-251` 的 `_position_clear` 把车体尺寸、相对速度和停车距离纳入生成/复位判断；`262-295` 只在驶出视野且位置合适时回收再生成，并用 generation/event 区分生命周期。应继承这套“可见性 + 几何净空 + 生命周期标识”，不要照搬旧的 −150 m 删除。

## 给新设计的结论

保留：每车状态机、独立决策时钟、候选车道安全复核、冲突仲裁、碰撞/回收出口。

重写：可复现随机源、完整状态初始化、基于道路弧长和车体几何的间隙/TTC、跟驰速度控制、变道持续期与取消条件、生成重试/生命周期策略。

审查结论仅来自静态代码证据；本文没有声称上述风险已经在旧程序中发生。
